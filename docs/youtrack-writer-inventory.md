## Notes

1. **Three tasks writes you may not expect.** (a) `createTask` writes no `task_events` row (A1). (b) A comment write does not touch `tasks` at all (A35), so the feed is the only place comment activity shows up (`sync_comments`), plus `import_export.go:50`. (c) `processNextLinearOutbox` UPDATEs `tasks.refs.linear` (linear.go:292), and `insertEvent` UPDATEs `tasks.last_activity_at` (task_flow.go:88), so a `tasks` row can change twice in one tx and emit two feed rows.
2. **Non-atomic seams today (candidate op-log sites):** YT-PQ after a PG commit (A16, A17); MCP task intake and audit (A6, audit is a separate tx); `tasks add` doc + task + translation (A2); Linear ask (A47: PG tx, Linear call, PG tx); YT comment push (A39: HTTP call then link INSERT); every `youtrack_*` map write after a YT call (A61-A63). Atomic multi-entity txs that b1-b6 would split: `ReplyDots` (A14, comment + doc + result + state + token + decision), `ResolveDecision` (A48, task JSON + attempts + resolutions + outbox + event + request rows), `PutDocument` for `deploy/*` (A42, document + task state moves), `IntakeTask` (A3, task + doc), YouTrack pull (A9/A38, comment + state + priority + lane + processed + cursor).
3. **Duplicate representations of one decision:** `tasks.refs.decision_request` JSON, `decision_requests` row (DECM), `sync_decisions` (trigger), `decision_answer_attempts` + `decision_resolutions` (append-only), `decision_deliveries`, `notification_outbox`, and (Linear) `linear_decision_issues`. b4 has to pick which one is the id-mapped record.
4. **Lock-order consequences** (internal/store/lockorder.go): `PutDocument` (deploy keys), `ApplyYouTrackActivity`, `ReplyDots`, `UpdateTask`, `ResolveDecision`, `IntakeTask`, `CreateDotsRequest` all take L2 first; the YouTrack pull and `ReplyDots` take L2, then CL, then the task row (lockorder.go "Other advisory locks"). Any op-log write added inside these txs must go after all of them and before the deferred `sync_allocate` (level 6).
5. **Search already has a YT backend** (`SearchBackend`, `Service.Search` api.go:244 and youtrack/search.go) but ctx/memory scopes and the PG fallback keep every PG body column in the read path (B1-B3).
6. **Docs say the opposite of the code in two places.** docs/mcp.md "Field ownership" table lists `title`, `body`, `body_doc` as `hk` PG-canonical (true today); docs/youtrack.md says Korean title/body are YouTrack-canonical but only the Korean `translations` title is pushed as the YT summary (sync.go:692), and there is no pull for title or description (A9 creates a task from a new issue's title only; there is no UPDATE of `tasks.title` anywhere).
7. **Console/dots parity:** docs/parity.md row "Edit a filed task's title or body" is `—` on every surface, consistent with A1/A3 (no title/body edit path).
